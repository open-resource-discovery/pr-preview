ORD Introduction

This introduction explains why ORD is needed, how it works, what it enables, and how SAP applies it.

🎦 There is also an ORD Introduction video, based on this article.

Why ORD?​

Resource metadata lives in silos​

Specialized standards describe individual resources well, but they do not provide a shared inventory of an application, service, or system landscape. System inventories, API catalogs, event catalogs, data catalogs, and agent registries often expose different formats and models. High-level context and relationships are expressed inconsistently, and static documentation can drift from what a running system actually exposes.

Shared provider metadata reduces custom adapters​

Without alignment on metadata description and discovery, consumers integrate separately with every provider and source format. The number of point-to-point integrations grows quickly, and each integration can require different implementation logic.

ORD addresses this through two ideas. Applications and services publish metadata through a shared protocol, and aggregators collect that metadata into views designed for discovery.

One Discovery API based on a connected metadata graph​

An ORD aggregator can combine provider metadata with information from other inventories and catalogs. It can connect resources through shared semantics and taxonomy, then expose the result through a discovery-oriented API. Consumers can use this connected view instead of implementing every source-specific adapter themselves.

An ecosystem can contain multiple aggregators, and a consumer may also read directly from a provider when that is appropriate.

How ORD works​

The protocol can be understood as a path from self-description and discovery to a connected, perspective-aware metadata view.

A protocol for self-description​

Open Resource Discovery (ORD) enables applications and services to publish a standard, machine-readable description of their resources and capabilities. This description can cover reusable static metadata as well as the complete metadata of a running system instance.

An ORD provider publishes ORD documents through its ORD Provider API. Those documents provide stable identity, lifecycle, visibility, taxonomy, and relationships, and they link to detailed resource definitions such as OpenAPI, AsyncAPI, OData CSDL, and A2A Agent Cards. Providers can also declare their use of external APIs, Events, or Capabilities through Integration Dependencies.

Three roles, clear responsibilities​

ORD distinguishes three roles, although one system can implement more than one role.

  • An ORD Provider publishes a self-description of an application or service.
  • An ORD Aggregator collects, validates, resolves, connects, and serves metadata from multiple providers.
  • An ORD Consumer retrieves metadata from an aggregator or directly from a provider.

ORD standardizes discovery, not everything​

ORD describes and connects resources. It inventories exposed resources and capabilities, links detailed definitions, adds shared identity and context, and standardizes publishing and discovery behavior.

ORD does not replace specialized resource-definition standards such as OpenAPI or AsyncAPI. It does not transport business data, configure runtime integrations, or discover a system before its location is known.

Discovery follows links from one known entry point​

An aggregator or direct consumer starts with a known system, reads its well-known ORD configuration, fetches the referenced ORD documents, and follows links to detailed definitions.

Try ORD with the reference application​

The ORD Reference Application provides a live example of this discovery flow. Its configuration points to ORD documents, and those documents describe APIs and Events together with taxonomy and links to their detailed definitions.

Resources become connected metadata​

ORD can describe APIs, Events, Data Products, Agents, Capabilities, and Integration Dependencies. Packages, Products, Vendors, Entity Types, Groups, Group Types, and Consumption Bundles provide organization, ownership, and shared context. Stable identifiers and explicit relationships connect these concepts.

Describe what is offered and what is running​

ORD uses perspectives to separate reusable design-time metadata from the complete metadata of a running system instance.

  • The static perspectives, system-type and system-version, describe a reusable baseline without tenant-specific context.
  • The dynamic perspective, system-instance, describes one complete running tenant, including relevant configuration, extensions, and endpoints.
  • The system-independent perspective describes shared taxonomy that exists outside a particular system context.

For a tenant, an aggregator uses a published system-instance perspective as the complete view. Only when that perspective has not been published may the aggregator resolve an effective static view. The perspectives concept page explains the complete resolution rules.

What ORD enables​

The same connected metadata foundation can support many experiences.

  • Catalogs can build searchable inventories across resource types and providers.
  • Developer tools can locate contracts, documentation, and access context programmatically.
  • Landscape tools can reveal capabilities and declared dependencies across systems.
  • Automation and AI can use structured, discoverable metadata as grounding and integration context.

SAP: shared metadata, connected views​

At SAP, the same applications and services can publish static metadata about what they offer and dynamic metadata about what is running. The two perspectives serve different discovery needs while using the same ORD protocol and resource identities.

  • Reference landscape: SAP Business Accelerator Hub aggregates static metadata to describe what products offer without requiring a provisioned tenant.
  • Customer landscape: Unified Metadata Service aggregates dynamic system-instance metadata and other landscape information to describe what is actually present for a customer.

The consumer names in the diagram are representative examples. The connections show metadata delivery and do not imply that every consumer uses every source.

Static view: SAP Business Accelerator Hub​

The SAP Business Accelerator Hub presents generic product documentation from the static perspective. It allows consumers to discover technical capabilities before they own or provision a system.

Dynamic view: Unified Metadata Service​

Unified Metadata Service (UMS), previously referred to here as Unified Customer Landscape (UCL), combines ORD information with other customer landscape metadata. Unlike the static product view, UMS can represent system-instance metadata, including customer-specific configuration, extensions, and endpoints.

The SAP BTP Cockpit System Landscape UI illustrates how customers can inspect systems and organize them into formations for supported integration scenarios.

UMS aggregates information about SAP, partner, third-party, and on-premise systems into a machine-readable landscape model. It re-exposes that model to tools that help customers understand, develop against, and manage their landscape. The metadata can also support automation of integration lifecycle tasks, including operational tasks such as credential rotation.

Start with one API and one useful consumer​

A focused pilot makes the value of ORD visible without requiring a complete landscape rollout.

  1. Provider: Publish a Package and one API Resource, link the existing OpenAPI definition, and expose the ORD configuration.
  2. Aggregator: Crawl and validate the metadata, resolve the effective view, and preserve metadata access boundaries.
  3. Consumer: Make the API discoverable in one catalog or developer tool through an aggregator or directly from its provider.

Start with describe → validate → discover, then add Entity Types, dependencies, and other metadata as the use case grows.
